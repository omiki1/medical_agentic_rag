01项目概览与定位

MediAtlas 是一套医学资料检索工作台。它把疾病知识、公开来源与对话上下文连接起来，输出可追溯、可验证的资料摘录，并在界面上展示检索、校验与停止的完整过程。

1.1 它到底是什么

用一句话概括：一个「宁可拒绝回答，也不编造答案」的医学 RAG + 受限 Agent 系统。它的核心价值不在「生成一段流畅的回答」，而在「回答中的每一句话都能在原文里逐字找到出处」。

1.2 它「不是」什么（边界意识）

这个项目最大的特点，是把「能做什么」和「不能做什么」都写在了脸上。理解这一点，就理解了整个系统的设计动机。

它不是医疗诊断工具不提供诊断、处方、剂量建议。遇到个人用药、剂量、孕妇/儿童/特殊人群问题，会主动拒绝回答（abstained）。
它不是「大模型自由发挥」的聊天机器人模型只能选择和排列原文片段，不能改写、不能推理补全。任何「不受原文支持」的内容都无法通过校验门。
它不是生产级多租户服务单机单进程、限流并发都在进程内，默认只绑定 localhost。这是刻意的「个人研究部署」范围。

1.3 五个状态（系统的全部出口）

状态含义触发示例
answered有来源支持，已通过证据+答案双重校验「高血压有哪些症状？」
abstained证据不足 / 涉及个人治疗，保守拒答「二甲双胍吃多少毫克？」
emergency识别到急症信号，先于模型执行「我突然胸痛而且喘不上气」
clarification缺少上下文，需要补充「那应该如何预防？」（无上文实体）
out_of_scope超出知识库范围「帮我查明天的天气」

2.2 为什么不用 LangGraph

框架 vs 手写的取舍LangGraph 提供了 streaming 和持久化，但本项目需要的是「有界状态、可观察事件、可逐条评测」的确定性。手写 Python 状态机 + 异步生成器让每一步都能产出 TraceEvent（执行轨迹），而模型的思维链永远不落库、不展示。详见 docs/ARCHITECTURE.md 第 26–32 行的说明。

03核心思路主线（先看懂这一章）

如果只记住一条主线，请记住这条：「先感知 → 再规划 → 检索证据 → 用代码设门槛 → 不够就受限反思 → 够了就用原文片段拼答案 → 拼出来的每一句都要逐字校验」。这一章用一张大图把全链路串起来。

一句话记忆钩子「模型负责提候选，代码负责设门槛」。模型的每一次输出（规划、反思、答案）都要经过 Pydantic 结构校验 + 白名单/逐字校验；代码（不是模型）决定能不能继续、能不能答。

3.1 两条「硬限制」主线

限制数值目的
检索轮数最多 3 轮防止无限反思循环
模型请求数最多 6 次成本 + 延迟双预算
单请求超时默认 75–90 秒SSE 不悬挂
单次模型请求20 秒LLM 慢响应熔断
全局并发10 个任务单进程容量；第 11 个明确拒绝
单用户进行中1 个避免重复计算

04系统架构与分层

后端采用「领域 MVC + 依赖装配根」的组织方式：按业务域（auth / user / chat / memory / rag）划分，每个域内再分 controller / service / dao / entity 层。这与常见的「按技术分层（routes / models / utils）」不同，是可维护性更强的做法。

4.1 目录结构总览

4.2 MVC 分层的职责边界

层职责不做什么
controllerHTTP 绑定、参数校验、依赖注入 owner不写业务逻辑、不写 SQL
service业务编排、状态转换、限流/幂等不直接操作 SQL
daoSQL 与持久化，所有查询带 owner不做业务判断
entityPydantic 请求/响应/领域对象不依赖 FastAPI
为什么要这么分？当 DAO 层每一条 SQL 都强制带 owner（会话 id）时，「跨用户越权读历史」这类 bug 在结构上就被挡住了。这正是 MVC 分层带来的结构性安全，而不只是写代码时的小心。

4.3 依赖装配根（ApplicationContext）

所有对象在 ApplicationContext.__init__ 中一次性装配，通过构造函数注入（没有全局 import 单例、没有 ServiceLocator）。这带来两个好处：可测试（测试里可以注入假 corpus/retriever）和生命周期清晰（一个进程只加载一次模型）。

backend/common/ApplicationContext.py（节选）

要点解读
  • corpus / retriever 可注入：这是测试的命门。tests/test_contracts.py 里就通过注入假数据目录来跑端到端测试，不碰真实模型。
  • 模型只加载一次：`HybridRetriever` 内部持有 SentenceTransformer 实例，进程启动时加载，之后复用。

05一次请求的完整生命周期

从用户在输入框敲回车，到答案带着 [E1][E2] 引注渲染出来，中间经过了 10 个关键环节。这一章用「泳道时序图」纵向看全链路。

5.1 SSE 事件流长什么样

前端收到的不是一次性 JSON，而是一串 text/event-stream 事件。每一种事件都对应「可观察」的一步：

SSE 事件序列示例
data: {"type":"start","run_id":"...","conversation_id":"..."}

data: {"type":"trace","data":{"step":"analyze","label":"识别问题与安全检查",...}}

data: {"type":"trace","data":{"step":"plan","label":"制定检索计划",...}}

data: {"type":"trace","data":{"step":"action","label":"执行受限检索工具",...}}

data: {"type":"trace","data":{"step":"observe","label":"观察检索结果与来源覆盖",...}}

data: {"type":"trace","data":{"step":"grade_evidence","label":"证据满足要求",...}}

data: {"type":"trace","data":{"step":"grade_answer","label":"逐项核验引用与覆盖范围",...}}

data: {"type":"result","data":{"status":"answered","answer":"... [E1] [E2]","evidence":[...]}}

data: {"type":"done","run_id":"..."}
要点解读
  • trace 事件只描述「实际执行的动作」，不包含模型思维链——这是可观察性与隐私的双重考量。
  • result 事件在流中只出现一次，且被 DAO 立即持久化；之后同一 request_id 重放直接返回结果。
  • 心跳：队列 10 秒无输出时发 : heartbeat，防止代理断连。

06核心链路逐段详解

这是全手册最重的一章。我们把主线拆成 8 个环节，每个环节讲「它在做什么 → 关键代码 → 代码为什么这么写」。读完这一章，你就真正「熟悉了这个项目」。

6.1 感知：QueryAnalyzer

backend/agent/QueryAnalyzer.py 是整个流程的入口。它在不调用任何模型的前提下，用规则完成四件事：实体提取、分面识别、急症检测、范围判断。

分面是后续「证据门槛」的重要维度：回答必须覆盖问题要求的每一个分面。比如「高血压如何预防」要求 prevention 分面，光有症状资料是不够的。

② 实体提取：最长别名优先 + 区间去重

QueryAnalyzer.py — extract()
def extract(self, query):
    lowered = query.lower()
    occupied = set()
    matches = []
    for alias, entity in self.aliases:   # 已按长度降序排序
        pattern = (r"(?<![a-z])" + re.escape(alias) + r"(?![a-z])") \
                  if alias.isascii() else re.escape(alias)
        for match in re.finditer(pattern, lowered):
            span = set(range(match.start(), match.end()))
            if span & occupied:    # 已匹配区域不重复匹配
                continue
            occupied.update(span)
            if entity not in matches:
                matches.append(entity)
    return matches[:6]
要点解读
  • 别名来自语料库：MedicalCorpus.aliases 在加载时构建，把「消渴症」「血糖病」都映射到「糖尿病」。所以「我老是喝水尿多变瘦」能通过 EXPANSIONS 词表转成「口渴/多尿/体重下降」，再命中症状分面。
  • 最长别名优先：先排长词再排短词，避免「高血压」被「血压」截断。
  • occupied 区间：防止同一段文字被两个别名重复计数。

③ 急症检测：否定范围处理

6.3 检索：多路召回 RAGService

backend/rag/service/RAGService.py 的 retrieve 是检索主入口，固定顺序：召回 → 图谱验证 → HyDE → 融合 → 过滤 → 重排 → 证据门槛。

自研 BM25：中文 bigram 分词

backend/rag/BM25Retriever.py — tokenize()
def tokenize(text):
    # Chinese bi-grams preserve exact medical terms without a language-model dependency.
    text = text.lower()
    result = re.findall(r"[a-z0-9]+", text)          # 英文/数字整体保留
    for segment in re.findall(r"[\u4e00-\u9fff]+", text):
        result.extend(segment[i : i + 2] for i in range(len(segment) - 1)
                      if segment[i : i + 2] not in STOP)   # 二字滑动窗口
    return result

没有引入 jieba 等分词库，用「二字滑动窗口」把中文切成 bigram。好处：零外部依赖、医学专有名词不会因分词错误而丢失；代价：召回偏宽，但后面有 CrossEncoder 精排兜底。

6.4 融合：加权 RRF（EvidenceFusion）

def fuse(*routes, k=20, weights=None):
    """Weighted reciprocal-rank fusion, one contribution per document per route."""
    weights = weights or {}
    merged = {}

        seen = set()
        for rank, ev in enumerate(route, 1):
            doc_id = ev.document.id
            if doc_id in seen:
                continue            # 同路重复不重复计分
            seen.add(doc_id)
            ...
            for method, contribution in contributions.items():
                item.fusion_contributions[method] = max(
                    item.fusion_contributions.get(method, 0), contribution)
            item.fusion_score = sum(item.fusion_contributions.values())
    results = sorted(merged.values(), key=lambda e: (-e.fusion_score, e.document.id))[:k]
要点解读
  • RRF 分数 = 1/(60 + rank)：排名越靠前贡献越大，常数 60 是业界常用的平滑项。
  • 同一文档多路命中只算一次：一个来源同时被 BM25 + Dense + Graph 命中，仍是「一份文档、一个出处」，不会因为被三个检索器命中就变成三份证据。
  • contributions 保留各路贡献明细：可追溯、可评测。

6.5 重排：CrossEncoder + 覆盖率兜底

backend/rag/RerankerUtil.py — rerank()
def rerank(self, query, evidence, analysis, k=None):
    ...
    for i, ev in enumerate(evidence):
        d = ev.document
        overlap = len(q & set(tokenize(d.title + d.text))) / max(1, len(q))
        entity_match = (not analysis.entities) or d.entity in analysis.entities
        facet_match = d.facet in analysis.facets or analysis.facets == ["overview"]
        ev.relevance = 0.45 * overlap + 0.3 * entity_match + 0.25 * facet_match
        if predictions is not None:    # 有 CrossEncoder 时
            score = float(predictions[i])
            ev.relevance = 0.5 * ev.relevance + 0.5 / (1 + math.exp(-max(-40, min(40, score))))
    evidence.sort(key=lambda e: (e.document.review_status != "source_checked", -e.relevance, ...))

两层设计：无模型时用「词重叠 + 实体匹配 + 分面匹配」的启发式打分（权重 0.45/0.30/0.25），有 CrossEncoder 时把它归一化成 0–1 后按 0.5/0.5 混合。最后排序键里 review_status != "source_checked" 排在最前，保证「已核验」永远优先。

6.7 反思：受限的反思循环（ReflectionService）

证据不足时进入反思。但反思不是让模型自由发挥，而是「在代码允许的动作里做选择」。

backend/agent/AgentPolicy.py — 白名单 + 校验
class AgentDecision(BaseModel):
    model_config = ConfigDict(extra="forbid")   # 多余字段直接拒绝
    action: Literal["rewrite", "hyde", "stop"]   # 只允许这三个动作
    query: str = Field(default="", max_length=400)
    reason_code: Literal["missing_facet", "vocabulary_gap",
                         "insufficient_sources", "no_progress"]

class AgentPolicy:
    """Code, never the model, grants capabilities and enforces the retry budget."""

    def allowed(self, analysis, iteration, progressed, dense_available, hyde_used):
        if (analysis.emergency or analysis.personal_treatment
            or analysis.constraints or iteration >= self.settings.max_iterations
            or not progressed):
            return ["stop"]    # 触发安全/上限/无进展 → 只能停
        actions = ["rewrite", "stop"]
        if dense_available and not hyde_used:
            actions.insert(1, "hyde")
        return actions
模型永远只是「提候选」ReflectionService.reflect 把模型返回的 JSON 交给 policy.validate()：如果 action 不在 allowed 白名单里，直接 raise ValueError。所以即使模型「想」执行 SQL 或访问网址，代码层直接拒绝——能力是代码授予的，不是模型自带的。

6.8 答案校验：AnswerGrader（防幻觉核心！）

这是本项目最有技术含量的一段。它的逻辑极其简单，却从机制上掐死了「模型瞎编」。

backend/agent/AnswerGrader.py — grade()（节选）
def grade(self, draft, evidence, analysis):
    by_id = {ev.document.id: ev for ev in evidence}
    for claim in draft.claims:
        if len(claim.evidence_ids) != len(claim.quotes):
            errors.append("引用与原文片段未一一对应")
        for doc_id, quote in zip(claim.evidence_ids, claim.quotes):
            ev = by_id.get(doc_id)
            if not ev or ev.document.review_status != "source_checked":
                errors.append("引用指向不可用证据")
            elif quote not in ev.document.text or len(quote.strip()) < 8:
                errors.append("引用片段不在来源原文中")
        # Exact extract mode: no model-written medical inference can pass this gate.
        if claim.text != "".join(claim.quotes):
            errors.append("出现不受原文支持的改写或推论")
    ...
    return AnswerGrade(grounded=not errors, relevant=relevant, complete=complete, ...)
理解这一行的价值普通 RAG 是「模型读文档，然后写一段自己的话」，幻觉风险靠 prompt 压制。这里反过来：模型只能「挑原文、排顺序」，输出的 text 必须等于所选 quotes 的机械拼接。校验器用纯代码（字符串相等 + 子串匹配）就能判断真假，不依赖模型自评。这就是为什么项目能坦然写「从机制上阻断幻觉」。

08四层记忆系统

项目实现了一套「四层记忆」：工作记忆 → 短期记忆 → 情节记忆 → 长期语义记忆。核心纪律是：用户的提问永远不会被「自动升级」成医学事实或诊断。

8.1 L2 的版本号设计（RedisMemory）

8.2 L4 的「明确确认」约束

为什么 L4 要「明确确认」？因为「长期记忆」如果让模型自动总结用户背景，很可能把「我最近咳嗽」这类陈述沉淀成事实，甚至暗示疾病。所以 MemoryService.remember 只接受用户主动点击确认的记忆，且 response_style 只允许「简洁/详细」两个值。测试里专门验证了：不确认的 memory 请求会返回 422。

9.2 同源索引：文档与图边共享 ID

backend/create_data/BuildMedicalCorpus.py — stable_id()
def stable_id(*parts: str) -> str:
    return hashlib.sha256("\x1f".join(parts).encode()).hexdigest()[:24]

文档 ID 是内容哈希（sha256(source_id, field, chunk_index, chunk_text) 的前 24 位）。这意味着：同样的内容永远得到同样的 ID → 天然去重；内容变了 ID 就变 → 版本可追溯；文档和它对应的图边共享同一个 source_id → 图谱与文本同源一致。

9.3 流式分块：真正的分块，不是假分块

BuildMedicalCorpus.py — chunks()（节选）
def chunks(text: str, limit=450, overlap=50):
    start = 0
    while start < len(text):
        end = min(start + limit, len(text))
        if end < len(text):
            stop = max(text.rfind(p, start + limit // 2, end) for p in "。！？；")
            if stop >= 0:
                end = stop + 1          # 优先在句末切
        yield text[start:end]
        if end == len(text):
            break
        start = max(start + 1, end - overlap)   # 50 字重叠

QA 长文本会被切出「独立片段」，而不是把整段拼成超长文档；每个片段独立成文档、独立建索引。测试里验证了「长文本确实被切成多段、每段 ≤450 字、ID 稳定」。

10.1 CSRF + Origin 双重校验

backend/common/RequestBoundary.py — 请求边界
async def dispatch(self, request, call_next):
    if request.method in {"POST", "PATCH", "DELETE"}:
        origin = request.headers.get("origin")
        if origin and origin not in self.settings.origins:
            return Response("Origin not allowed", status_code=403)
        length = request.headers.get("content-length", "0")
        if not length.isdigit() or int(length) > 32768:
            return Response("Request too large", status_code=413)
        body = bytearray()
        async for chunk in request.stream():
            body.extend(chunk)
            if len(body) > 32768:
                return Response("Request too large", status_code=413)
    response = await call_next(request)
    response.headers["X-Content-Type-Options"] = "nosniff"
    ...
    if request.url.path not in {"/docs", "/redoc"}:
        response.headers["Content-Security-Policy"] = "default-src 'self'; ..."

def hash_password(password):
    salt = secrets.token_bytes(16)
    digest = hashlib.pbkdf2_hmac("sha256", password.encode(), salt, 600_000)
    return "pbkdf2_sha256$600000$" + b64(salt) + "$" + b64(digest)

def verify_password(password, encoded):
    if encoded.startswith("$2"):      # 兼容原项目 bcrypt
        return bcrypt.checkpw(password.encode(), encoded.encode())
    method, iterations, salt, expected = encoded.split("$")
    if int(iterations) > 1_000_000:   # 拒绝异常高迭代 DoS
        return False
    actual = hashlib.pbkdf2_hmac("sha256", password.encode(), b64decode(salt), int(iterations))
    return hmac.compare_digest(actual, b64decode(expected))  # 常数时间比较

12.1 自研 SSE 解码器

frontend/src/api/ApiClient.js — SSEDecoder（节选）
export class SSEDecoder {
  constructor() { this.buffer = '' }
  feed(text, final = false) {
    this.buffer += text
    if (this.buffer.length > 2_000_000) throw new Error('服务返回的数据过大')
    const frames = this.buffer.split(/\r?\n\r?\n/)
    this.buffer = frames.pop()
    if (final && this.buffer.trim()) throw new Error('数据流意外中断')
    return frames.flatMap(frame => {
      const data = frame.split(/\r?\n/).filter(l => l.startsWith('data:'))
                        .map(l => l.slice(5).trimStart()).join('\n')
      return data ? [JSON.parse(data)] : []
    })
  }
}

不用 EventSource 而用 fetch + ReadableStream，是因为要支持 POST + 自定义头（CSRF）+ AbortController 取消。解码器按空行分割帧、累积 buffer 处理「半个帧」的情况，是标准 SSE 解析的严谨写法。

    result.duration_ms = round((time.perf_counter() - start) * 1000)
    yield {"type": "result", "data": result.model_dump(mode="json")}
读懂这段就懂了整个项目注意三个关键点：
  1. yield event(...) 无处不在——每一步都向外广播可观察事件，这是「可观察性」的来源。
  2. fingerprint + progressed——如果这轮检索出的文档集合和上一轮一模一样（无进展），直接 stop，防止空转。
  3. draft is None 兜底——模型选了两次都过不了校验，就回退到规则摘录（self.extract），规则摘录天然是「原文拼接」，必过校验。

13.2 兜底摘录 extract()：为什么它能保证安全

MedicalAgent.py — extract()（节选）
def extract(self, evidence, analysis, memory=None):
    selected = []
    covered = set()
    for ev in evidence:
        d = ev.document
        if analysis.facets != ["overview"] and d.facet not in analysis.facets:
            continue
        key = (d.entity, d.facet)
        if key in covered:
            continue          # 每个实体×分面只取一条
        covered.add(key)
        selected.append(Claim(text=d.text, evidence_ids=[d.id], quotes=[d.text]))
    ...
    return Draft(claims=selected[:8])

规则摘录直接把 text 设成 d.text、quotes 设成 [d.text]，所以 text == quotes 拼接 恒成立，天然通过校验。这就是「模型失败时系统依然能给出安全答案」的兜底机制。

13.3 渲染与免责声明

MedicalAgent.py — render() + 常量
DISCLAIMER = "以上为资料检索与医学科普，不构成个体诊断或处方；请结合医务人员评估。"
EMERGENCY_ANSWER = "你描述的情况可能需要紧急医疗处理。请立即联系当地急救服务..."

def render(self, draft, evidence, analysis):
    ids = {e.document.id: e.citation_id for e in evidence}
    body = "\n\n".join(
        claim.text + " " + " ".join(f"[{ids[i]}]" for i in claim.evidence_ids)
        for claim in draft.claims
    )
    return body + "\n\n" + DISCLAIMER

每条 claim 后面直接拼引注 [E1]，最后加固定免责声明。答案的「可追溯」在这里落实成文本层面的引注。

一份成熟的工程文档，必然包含「承认自己的边界」。这一章梳理项目里明确写出的取舍，帮你理解「哪些是刻意的、哪些是待改进的」。

14.1 刻意的边界（设计使然）

边界为什么刻意影响

14.2 已知的技术欠账

文档里明确承认的（docs/ARCHITECTURE.md）
  • GPU 同步推理：HTTP 取消无法强制终止已进入的 CUDA 运算，只能取消结果输出，那批计算可能跑完。
  • 限流在进程内：多实例需迁移到共享限流、连接池、外部任务队列。
  • 访客会话：过期后无法访问，但数据库行不自动删除——正式部署前需增加保留周期、备份与删除审计。
  • 急症规则：中英文规则 + 否定处理，不是临床分诊模型，未知表达可能遗漏。
  • 评测：开发回归集，非无偏外部评测；没有医生标注。

14.3 医学层面的硬边界

三条不可逾越的红线
  1. 图谱没有边 ≠ 药物禁忌：图谱里查不到「A 病和 B 药」的关系，不代表安全。
  2. 引用可验证 ≠ 医学正确：代码能证明「这句话来自原文」，但无法证明「原文本身医学正确」。
  3. 个人用药/剂量/特殊人群：一律需要专门证据 + 专业评估，普通科普页永远无法满足，系统强制拒答。

15面试问答与术语表

最后一章是「快速回顾」。熟读这一章，你可以在面试里用 3 分钟讲清楚这个项目。

15.1 高频面试问答

Q1：一句话介绍这个项目？
一个医学资料检索 RAG + 受限 Agent 系统，核心特点是「答案逐字摘录校验」——模型只能选择和排列原文片段，任何改写或推论都会被代码拒绝，从而从机制上阻断幻觉。
Q2：RAG 部分你具体做了什么？
自研 BM25（中文 bigram 分词）+ SentenceTransformer 向量 + 同源知识图谱三路召回，用加权 RRF 融合（每路每文档只计一次分），再用 CrossEncoder 精排；无模型时退化为覆盖率启发式打分。
Q3：Agent 的「受限」体现在哪？
模型输出永远只是候选数据。动作白名单只有 rewrite/hyde/stop（Pydantic Literal 约束 + extra=forbid），能力由代码授予；Neo4j 只有固定参数化只读查询；检索工具由程序装配，模型不能指定任意 SQL/网址/写入。
Q4：四层记忆怎么设计的？
L1 工作记忆（请求对象）、L2 短期（Redis，带 revision 版本校验，挂了回退）、L3 情节（PG 持久化问答）、L4 长期语义（仅用户明确确认的偏好，绝不推断诊断）。所有层都按 owner 隔离。
Q5：你的评测说明了什么？
32 条开发回归集，验证路由、引用和检索的工程正确性（路由/安全通过率 100%，Rerank 后 nDCG@5=0.98）。但它不是无偏外部评测，不代表临床正确率——这是刻意的诚实。
Q6：这个项目最大的技术难点/亮点？
可验证性设计：text == "".join(quotes) 这一行让答案校验变成纯字符串判定，不依赖模型自评，把「防幻觉」从 prompt 工程变成机制保证。
Q7：如果让你继续迭代，你会做什么？
① 建独立留出测试集（哪怕通过率降下来，更有说服力）；② 扩充 source_checked 语料拓宽可回答面；③ 多实例部署的共享限流/任务队列；④ 引文高亮定位等前端演示增强。

15.2 术语表

RAGRetrieval-Augmented Generation检索增强生成：先从知识库检索相关资料，再让模型基于资料作答。
RRFReciprocal Rank Fusion倒数排名融合：把多个检索器的排名按 1/(k+rank) 加权合并。
HyDEHypothetical Document Embeddings假设文档嵌入：让模型先写一个「假设答案」，用它去检索，缓解「问题短、语义稀疏」。
CrossEncoder交叉编码器把 query 和 doc 拼在一起打分，比双塔向量更准但更慢，用于精排。
SSEServer-Sent Events服务器向浏览器单向推送事件流，本项目用它实时展示执行轨迹。
bigram二元组把中文按相邻两个字切分（如「高血压」→「高血」「血压」），无词典依赖的分词方式。
owner数据归属标识每条数据记录所属的会话/账户 id，所有查询强制带它实现跨用户隔离。
source_checked来源已核验唯一能作为答案证据的文档状态；其余 unreviewed 文档只能浏览检索。
abstained保守拒答证据不足或涉及个人治疗时的系统状态，体现「宁可拒答不编造」。
指纹fingerprint / signature模型文件或数据内容的哈希，用于绑定索引版本、防止维度相同但模型不同的索引混用。
